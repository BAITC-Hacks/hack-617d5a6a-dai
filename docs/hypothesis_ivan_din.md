# Рабочая гипотеза

## Суть гипотезы

Среди клиентов, связанных с 81 известным `gid`, есть узлы, к которым сходятся маршруты переводов от нескольких известных клиентов. Мы предполагаем, что часть этих маршрутов сохраняет порядок дат и повторяется. Такие узлы станут проверяемыми кандидатами на роли консолидаторов или координаторов. Месячный граф показывает также маршруты, в которых исходящий перевод посредника случился раньше входящего. Если учитывать дату каждого перевода, список кандидатов на проверку изменится.

Это гипотеза о наблюдаемой структуре, а не утверждение о виновности, общем владельце счетов или движении одних и тех же денег. Исходные числа и требования к выходам взяты из официального ТЗ. Повторяемость и влияние порядка дат на список кандидатов предстоит проверить на выданных транзакциях.

## Как проверяем

Иван сначала считает для каждого узла число известных клиентов, связанных с ним маршрутами в месячном графе. Для кандидатов в хабы проверяет число разных плательщиков и суммы. Направление переводов также входит в базовый рейтинг. Затем считает маршруты с последовательными датами отдельных переводов и проверяет повторение маршрута в разные дни. Совпадение дат помечает отдельно: время внутри дня неизвестно. Так получается экспериментальный рейтинг с учётом порядка дат. Разница между рейтингами не доказывает, что один из них точнее.

Сравнение двух рейтингов покажет вклад времени: состав топ-20 до проверки дат и после неё, а также число узлов, для которых месячный граф показывает связь от известного клиента, но порядок дат её не поддерживает. Если в двух топ-20 совпадают хотя бы 18 узлов, временная часть гипотезы почти не меняет ранжирование. Тогда она остаётся пояснением к маршрутам. Быстроту работы аналитика этим тестом не измеряем.

## Что строим

Сначала выполняем обязательную часть ТЗ: один запуск принимает три Parquet и создаёт `nodes_roles.csv`, `clusters.csv` и `top_nodes.csv` менее чем за пять минут. Нужны роли всех 2 248 узлов, объяснимые критерии, топ не менее 20 узлов и граф с поиском по `gid`. Схемы обязательных CSV не меняем.

После готовности обязательной части добавляем проверку порядка отдельных переводов на выбранном маршруте `A → B → C`:

| Даты переводов | Текст на экране |
| --- | --- |
| `A → B` раньше `B → C` | Порядок дат поддерживает маршрут |
| Оба перевода в один день | Порядок внутри дня неизвестен |
| `B → C` раньше `A → B` | Эти переводы не подтверждают путь A → B → C |

Связи остаются видимыми при любом статусе. Статус относится к показанным транзакциям. Даже правильный порядок дат не доказывает, что через B прошли именно деньги A. Для узлов на четвёртом колене отсутствие исходящих объясняем обрывом выгрузки.

## Передача между Иваном и Дином

Иван рассчитывает роли и кластеры. Он формирует приоритеты и три CSV. Для карточки узла передаёт `gid`, `role` и `role_score`. Кластер и приоритет передаются полями `cluster_id` и `priority_score`. Также передаёт `evidence` и направленные связи. Если временная проверка готова, отдельно передаёт показанный маршрут с датами транзакций и одним из трёх текстовых статусов. При совпадении дат порядок не угадывает. Правило выбора маршрута и пороги фиксирует в README. В CSV `gid` остаётся `int64`, а в данных для браузера передаётся строкой.

Дин показывает поиск по `gid` и направление переводов. В карточке видна роль. Там же указаны кластер и приоритет. Объяснение расположено рядом с ними. По выбранному маршруту видны даты и текстовый статус; цвет служит дополнительным сигналом. Отдельно показано ограничение данных, которое влияет на вывод. Поиск сравнивает строковые `gid`, чтобы сохранить точность больших идентификаторов.

## Критерии проверки

- Запуск по README создаёт три обязательных CSV с точными колонками ТЗ. В `nodes_roles.csv` есть 2 248 строк; `evidence` заполнен и не длиннее 200 символов.
- Для трёх произвольно названных `gid` команда находит узел на экране и объясняет роль по рассчитанным признакам.
- Проверочный пример: `A → B` 18 июля и `B → C` 2 июля остаются двумя видимыми переводами, но путь A → B → C не называется подтверждённым движением денег. При одной дате выводится «порядок неизвестен».
- На реальных данных команда показывает два топ-20 и число узлов, для которых проверка дат изменила оценку маршрута. Если рейтинги почти совпадают, команда не заявляет, что временная проверка улучшила ранжирование.

Отдельная продуктовая гипотеза: карточка поможет аналитику быстрее выбирать следующий `gid`. Её можно проверять сравнением времени ручного разбора одного и того же узла с работой по карточке. Пока такого измерения нет.
