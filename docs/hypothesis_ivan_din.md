# Гипотеза для Ивана и Дина

Статус: гипотеза для проверки на данных кейса. Она не утверждает, что выявлены виновные клиенты или движение конкретных денег.

Числа, состав входа и обязательные выходы ниже взяты из официального ТЗ организаторов. Улучшение работы аналитика пока не проверено.

## 1. Результат для аналитика

AML-аналитик получает 81 известный `gid` и должен решить, кого из 2 248 клиентов проверить следующим. Наша гипотеза: список приоритетных узлов с объяснением роли, маршрутом переводов по датам и пометкой пробелов в данных позволит аналитику принять это решение быстрее и не принять связь на месячном графе за подтверждённый путь денег.

Проверяемое действие: аналитик открывает произвольный `gid`, видит входящие и исходящие связи, читает основание роли и выбирает следующий запрос для проверки гипотезы. Выигрыш времени и снижение числа ошибок пока не измерены.

## 2. Что строим

Сначала выполняем обязательную часть ТЗ: один запуск принимает три Parquet и создаёт `nodes_roles.csv`, `clusters.csv` и `top_nodes.csv` менее чем за пять минут. Нужны роли всех 2 248 узлов, объяснимые критерии, топ не менее 20 узлов и граф с поиском по `gid`. Схемы обязательных CSV не меняем.

После готовности обязательной части добавляем проверку порядка отдельных переводов на выбранном маршруте `A → B → C`:

| Даты переводов | Текст на экране |
| --- | --- |
| `A → B` раньше `B → C` | Порядок дат поддерживает маршрут |
| Оба перевода в один день | Порядок внутри дня неизвестен |
| `B → C` раньше `A → B` | Эти переводы не подтверждают путь A → B → C |

Связи остаются видимыми при любом статусе. Статус относится к показанным транзакциям. Даже правильный порядок дат не доказывает, что через B прошли именно деньги A. Для узлов на четвёртом колене отсутствие исходящих объясняем обрывом выгрузки.

## 3. Передача между Иваном и Дином

Иван рассчитывает роли и кластеры. Он формирует приоритеты и три CSV. Для карточки узла передаёт `gid`, `role` и `role_score`. Кластер и приоритет передаются полями `cluster_id` и `priority_score`. Также передаёт `evidence` и направленные связи. Если временная проверка готова, отдельно передаёт показанный маршрут с датами транзакций и одним из трёх текстовых статусов. При совпадении дат порядок не угадывает. Правило выбора маршрута и пороги фиксирует в README. В CSV `gid` остаётся `int64`, а в данных для браузера передаётся строкой.

Дин показывает поиск по `gid` и направление переводов. В карточке видна роль. Там же указаны кластер и приоритет. Объяснение расположено рядом с ними. По выбранному маршруту видны даты и текстовый статус; цвет служит дополнительным сигналом. Отдельно показано ограничение данных, которое влияет на вывод. Поиск сравнивает строковые `gid`, чтобы сохранить точность больших идентификаторов.

## 4. Приёмка Амира

- Запуск по README создаёт три обязательных CSV с точными колонками ТЗ. В `nodes_roles.csv` есть 2 248 строк; `evidence` заполнен и не длиннее 200 символов.
- Для трёх произвольно названных `gid` команда находит узел на экране и объясняет роль по рассчитанным признакам.
- Проверочный пример: `A → B` 18 июля и `B → C` 2 июля остаются двумя видимыми переводами, но путь A → B → C не называется подтверждённым движением денег. При одной дате выводится «порядок неизвестен».
- На реальных данных команда показывает число найденных маршрутов каждого статуса по принятому правилу выбора. Если маршрутов с обратным порядком нет, сообщает ноль и не заявляет, что временная проверка улучшила рейтинг.

Следующий исследовательский шаг: сравнить ручной разбор одного и того же `gid` с карточкой решения. Только после такого сравнения можно утверждать, что аналитик экономит время или реже ошибается.
