# Проверка решения AML четырьмя методами

Дата: 23.09.2026. Проверяемый вариант: обязательные роли, кластеры, очередь проверки и граф из ТЗ. Дополнение: карточка выбранного `gid` с исходными переводами, границей вывода и следующим запросом. Нелинейное экономическое время рассматривается как версия расчётов, а не как установленная связь между конкретными деньгами.

Факты о кейсе взяты из [официального ТЗ](../task/HackAlem_AI_Граф_денег_восстановление_финансовой_структуры_организованной.md). Метод проверки взят из личных рабочих материалов Амира по четырём названным ниже подходам. Эти материалы не подтверждают спрос банка.

## AJTBD: работа аналитика

Работа без названия продукта: когда правоохранительные органы передали известных клиентов нижнего уровня, аналитик хочет найти следующих клиентов для углублённой проверки и объяснить выбор по наблюдаемым операциям. По ТЗ он начинает с 81 `gid`, вручную трассирует переводы на четыре колена и выбирает приоритет интуитивно. Числа и описание процесса имеют статус `source_defined`; работа конкретного банка нами не наблюдалась.

Критическая последовательность: принять список → проверить охват выгрузки → найти кандидатов вне исходной группы → сверить основание роли с отдельными переводами → выбрать следующий `gid` → сформулировать запрос дополнительных сведений. Роль и скор закрывают только часть этой работы. Если аналитик после открытия карточки снова вручную восстанавливает все основания, карточка не устранила работу.

Big Hire: банк решает внедрить инструмент. Кто платит и кто утверждает внедрение, `not_validated`. Little Hire: аналитик использует карточку при выборе очередного клиента. Силы переключения и эмоциональный результат описаны как `hypothesis` в [карте AJTBD](./aml_analyst_ajtbd.md); интервью с аналитиком не было.

Проверка: на одинаковых эпизодах сравнить ручной выбор клиента с выбором по карточке. Измерить время до обоснованного следующего запроса и число выводов, для которых не найдены исходные переводы. Без этого сокращение труда остаётся `not_validated`.

## СГО: единица ценности и издержки

Названная ТЗ альтернатива: ручная трассировка и интуитивный приоритет. Сравнение с действующим AML-продуктом банка невозможно без описания его функций. Старая единица результата для нашего сравнения: позиция в рейтинге и роль. Новая единица: кандидат на проверку с основанием и следующим запросом. Эта смена имеет смысл, если аналитик действительно тратит меньше усилий на подготовку решения.

| Ход | Действие в этом кейсе |
| --- | --- |
| Устранить | Ручную сборку основания по разным представлениям данных для выбранного `gid`, если такая работа есть в реальном процессе |
| Снизить | Число операций на первом экране до тех, которые объясняют роль и приоритет; полная история остаётся доступной |
| Повысить | Проверяемость причин выбора по отдельным переводам и явность границы выгрузки |
| Создать | Следующий запрос по кандидату с указанием, какой пробел он закрывает |

Сдерживание затрат реализации: расчёт из четырёх выданных полей по фиксированным правилам; без обучения модели и догадки о пропущенных операциях. Затраты аналитика на перепроверку пока неизвестны. Конкурентная кривая не построена. Неклиенты и скачок полезности не подтверждены. Поэтому это `hypothesis` СГО, а не доказанный голубой океан.

## ТРИЗ: какое противоречие реально

Хотим сохранить возможную экономическую связь при предварительном финансировании. Если считать любой маршрут реальным движением денег, получим ложное подтверждение при обратном порядке дат. Если удалить маршрут, потеряем наблюдаемые переводы и возможную версию позднего возмещения. Один и тот же маршрут требуется сохранить как объект проверки и исключить как подтверждённый поток конкретных денег.

Разделение по смыслу снимает конфликт. Слой наблюдений хранит оба перевода. Слой физически допустимого потока допускает только порядок дат, а совпадение дней помечает неизвестным. Слой версий оставляет предварительное финансирование возможным, но не присваивает ему риск без отдельной проверки. ИКР: аналитик видит различие без ручной сверки каждой пары дат; утверждения о собственнике средств система не делает. Ресурс уже дан кейсом: `src`, `dst`, `date`, `sum_kzt`.

Практический вариант: один статус в карточке плюс исходные операции. Альтернатива: два фильтра графа, «все наблюдаемые связи» и «маршруты с подтверждённым порядком дат». Первый вариант дешевле для пятичасового кейса. Выбор между ними по сроку разработки является обычной приоритизацией, а не отдельным приёмом ТРИЗ. Разделение смыслов можно назвать разрешением противоречия, но оно не доказывает существование предварительного финансирования.

## Морейнис: продуктовая проверка

| Ворота | Что известно по кейсу | Статус |
| --- | --- | --- |
| Старый расход | ТЗ говорит о часах ручной трассировки на узел | `source_defined`; расход конкретного банка не измерен |
| Покупатель и конкурент | Пользователь назван: AML-аналитик. Ручной способ назван ТЗ. Владелец бюджета и реальный критерий выбора неизвестны | `not_validated` |
| Почему возможно сейчас | Пайплайн на выданных данных можно построить. Изменение, которое сделало продукт возможным именно сейчас, не установлено | `not_validated` |
| Проверка спроса | Демо может доказать работоспособность. Согласия банка на пилот или оплату нет | `not_validated` |
| Экономика одной продажи | Нет цены, стоимости внедрения, человеческой проверки и поддержки | `not_validated` |
| Первый рынок | Один конкурсный кейс не показывает плотность повторяемых покупок банков | `not_validated` |

По исправленной логике Морейниса эти неизвестные нельзя компенсировать баллами за техническое демо. Для конкурса надо выполнить ТЗ и показать проверяемое преимущество в одном рабочем эпизоде. Для продуктового вывода нужен разговор с владельцем AML-процесса о последнем случае, текущем инструменте, критерии выбора и следующем действии, на которое он согласится.

## Решение для команды

Проверка четырьмя рамками не меняет обязательный объём ТЗ. Иван должен показать на произвольном `gid` расчёт роли и места в очереди с конкретными переводами. Дин должен дать аналитику возможность открыть эти переводы из топ-листа и увидеть следующий запрос. Амир проверяет, может ли по этому экрану за минуту объяснить выбор без устного перевода разработчиков.

Отрицательный лаг остаётся исследовательским наблюдением. В предварительном подсчёте он не дал сильного отличия от перестановок дат: 45 узлов в исходных данных против среднего 38,5 в 100 перестановках, в восьми перестановках результат был не ниже 45. Эти числа имеют статус `observed` для одного мотива. Они не дают основания повышать `priority_score` и не подтверждают координацию. Подробности в [гипотезе для Ивана и Дина](./hypothesis_ivan_din.md).
