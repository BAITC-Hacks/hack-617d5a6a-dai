# DAI: «Граф денег»

Командный репозиторий HackAlem AI. Задача кейса: восстановить проверяемую структуру финансовой сети по направленному графу переводов и определить порядок проверки клиентов.

## Текущий результат

Пайплайн (`pipeline/`, метод v1 по умолчанию) считает роли по опубликованным правилам, кластеры Louvain и единый приоритет для 2 248 узлов. Запуск на чистом клоне с Python 3.13.5 занял 28,6 секунды после загрузки библиотек. Выгрузки прошли 49 проверок `pipeline/check.py`; результат совпал с CSV в репозитории байт в байт. В `evidence` записаны два признака с наибольшим вкладом в приоритет. Стартовый код организаторов находится в `task/starter/`.

## Локальный запуск

Пайплайн без Docker. Сначала проверьте версию Python:

```bash
python3 --version  # нужна версия 3.11, 3.12 или 3.13
make setup      # .venv и зависимости из requirements.txt
make pipeline   # task/data/*.parquet → outputs/nodes_roles.csv, clusters.csv, top_nodes.csv
make check      # проверка выгрузок по схеме ТЗ, код возврата 1 при нарушении
```

Если системный `python3` другой версии, создайте окружение поддерживаемой версией. Например, с установленным `uv`:

```bash
uv venv --python 3.13 .venv
uv pip install --python .venv/bin/python -r requirements.txt
make pipeline
make check
```

Команды без make при поддерживаемом `python3`:

```bash
python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
python -m pipeline.run --data task/data --out outputs
```

Интерфейс: `make api` (FastAPI на 8000, читает `outputs/`; без выгрузок отдаёт заглушку с пометкой `mock`) и в другом терминале `make web` (http://localhost:5173). Подробнее: [backend/README.md](backend/README.md), [dai-front/README.md](dai-front/README.md). Пороги ролей и приоритета заданы в `pipeline/rules.py`. Функция `print_thresholds()` печатает таблицу порогов для README. При запуске значения записываются в `outputs/run_meta.json`. Запасной метод v0: `python -m pipeline.run --data task/data --out outputs --method v0`.

## Задача аналитика

1. Аналитик получает от правоохранительных органов 81 известный `gid`.
2. Пайплайн по выгрузке переводов на 4 колена присваивает каждому из 2 248 узлов роль и кластер. Для очереди проверки он рассчитывает приоритет с числовым основанием.
3. В интерфейсе аналитик ищет `gid` и смотрит направления переводов. Карточка объясняет роль и приоритет; список помогает выбрать следующего клиента для проверки.

Выводы о клиентах служат гипотезами для проверки. Они не устанавливают виновность.

## Как читать приоритет

Приоритет помогает выбрать, кого проверить первым. Семь показателей описывают суммы переводов, число разных плательщиков и получателей, положение клиента между другими клиентами, меньшую из входящей и исходящей сумм и число исходных клиентов, связанных с ним по графу. Редкое значение даёт больше баллов. Повторные пары переводов похожей суммы за 0–2 дня добавляют один балл к сумме. Клиент попадает в очередь проверки, если хотя бы два из семи показателей входят в верхние 5 % среди 2 248 клиентов. Сумма баллов задаёт порядок внутри очереди и за её пределами. Значение 6 баллов служит справочным порогом суммы и не определяет очередь. Список `top_nodes.csv` содержит 50 клиентов независимо от очереди. Баллы не показывают вероятность нарушения. В карточке приведены два показателя с наибольшим вкладом.

В `nodes_roles.csv` поле `priority_score` лежит в пределах 0..1. Справочное значение 6 относится к исходным баллам в дополнительном поле `priority_raw`. Роли описывают видимые направления переводов. Они не устанавливают, кто распоряжается счетами и кому принадлежат деньги после поступления.

## Как проверить вывод

Откройте интерфейс и введите `gid` из [пяти контрольных случаев](docs/acceptance.md). Проверьте направление стрелок и даты переводов. Сравните роль в карточке с CSV. Отдельно проверьте два основания приоритета и следующий запрос. Затем попробуйте произвольный `gid` из `nodes_roles.csv`. Команды приведены в разделе «Локальный запуск».

## Ограничения выгрузки

В данных есть внутрибанковские переводы за июль 2026 года на сумму от 5 000 KZT. Обход начат от 81 исходного клиента и идёт по исходящим переводам до четвёртого шага. Входящие переводы клиентов вне найденной выборки не видны. У 444 клиентов четвёртого шага исходящие переводы не собирались. Отсутствие исходящих у такого клиента не означает, что он сохранил полученные деньги. Время внутри дня неизвестно. Остатки и сведения об управлении счетами отсутствуют. Роли в данных не размечены, поэтому точность классификации по эталонным ответам не измеряется.

Мы проверили два признака по датам. Выход раньше похожего входа встречался и после случайной перестановки дат примерно с той же частотой, поэтому этот порядок не повышает приоритет. Повторный перевод похожей суммы через 0–2 дня встречался у 54 клиентов; при перестановке дат таких клиентов было 34–38. Такой признак добавляет к приоритету один балл. Сопоставление дат и сумм не доказывает, что через счёт прошли те же деньги. Проверку можно повторить командой `python -m pipeline.temporal_check --data task/data` после установки зависимостей.

## Критерии готового решения

- Один локальный запуск из исходных Parquet создаёт три CSV за 5 минут на обычном ноутбуке. Для обязательного расчёта не нужны платный API, GPU или секретный ключ.
- `nodes_roles.csv`: все 2 248 узлов, объяснимые роли и числовые основания; `clusters.csv`: группы и гипотезы; `top_nodes.csv`: минимум 20 приоритетных узлов.
- Интерфейс показывает направление переводов и связи произвольного `gid` за время демо. Роль видна в карточке.
- Правила назначения ролей, пороги, ограничения выборки и план масштабирования описаны в README/`docs/`. Выводы о клиентах формулируются как гипотезы для проверки.

`gid` хранится как `int64` в данных и обязательных CSV. При передаче идентификаторов в браузер используйте строки: некоторые значения больше безопасного целого JavaScript.

Секреты хранятся только локально в переменных среды или `.env`; `.env` не коммитится. Опциональные LLM-функции не должны быть нужны для воспроизведения обязательного результата.
